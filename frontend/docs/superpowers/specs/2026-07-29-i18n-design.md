# i18n Design — ATS AI Resumer Frontend

## Goal
Internationalize the entire frontend UI (landing + authenticated app) with `pt-BR` (default/fallback) and `en`, using `react-i18next`.

## Libraries
- `i18next`
- `react-i18next`
- `i18next-browser-languagedetector`

## Language detection & persistence
- Detector order: `localStorage` → browser `navigator.language` → fallback `pt-BR`.
- `localStorage` key: `i18nextLng` (library default).
- No backend/profile persistence — client-only.

## File structure
```
src/i18n/
  index.ts                # i18next.init(), detector, resources
  locales/
    pt-BR/
      common.json          # shared: buttons, generic actions, form validation, states (loading/empty/error)
      landing.json         # Navbar, Hero, Features, HowItWorks, DashboardPreview, Benefits, Testimonials, CTA, Footer
      auth.json            # Login, Register, AuthShell, BrandCardMarquee
      layout.json          # AppShell, Sidebar, Topbar, PageHeader, CommandPalette, NotificationsPopover
      dashboard.json        # Dashboard page + dashboard/* components
      resumes.json           # Resumes, ResumeDetail, Versions, History, Export pages + resume/*, export/* components
      analysis.json           # analysis/* components (BulletRewrites, IssuesList, KeywordChips, ScoreBreakdown, StrengthsList)
      insights.json
      settings.json
    en/
      (mirror of the above)
```
Namespaces are loaded eagerly (bundled at build time via static import), no lazy backend loading — the app is small enough that this is simpler than an HTTP backend plugin.

## Setup
- `src/i18n/index.ts` initializes i18next with all namespaces/resources and is imported once, before `<App />` renders, in `src/main.tsx`.
- Default namespace: `common`. Components pull in the namespaces they need via `useTranslation(["landing", "common"])` etc.

## Language switcher
- New component `src/components/layout/LanguageSwitcher.tsx`: small dropdown (🇧🇷 PT-BR / 🇺🇸 EN) using existing `ui/` primitives and `cn()` conventions.
- Mounted in two places:
  - `Navbar` (landing, public)
  - `Settings` page, under a "Preferences" section (authenticated area)
- On change: `i18n.changeLanguage(lng)` (the detector plugin persists to `localStorage` automatically).

## Migration approach
Work through the codebase in passes, replacing hardcoded JSX strings with `t("key")` calls and populating both locale files together (pt-BR authored first since it's the team's language, en translated alongside):
1. Infra: install deps, `src/i18n/index.ts`, wire into `main.tsx`, `LanguageSwitcher` component.
2. Landing: `pages/Landing.tsx` + `components/landing/*`.
3. Auth: `pages/Login.tsx`, `pages/Register.tsx`, `components/auth/*`.
4. App shell/layout: `components/layout/*` (nav labels, menu items, tooltips).
5. Internal pages: `Dashboard`, `Resumes`, `ResumeDetail`, `Export`, `Insights`, `Versions`, `History`, `Settings`, `Placeholder`, and their supporting components (`dashboard/*`, `resume/*`, `export/*`, `analysis/*`).

`ui/*` primitives (Button, Card, Input, etc.) are generic/unstyled-content components — they take labels as props from callers and generally need no changes unless they contain their own literal copy (e.g. a default placeholder string).

## Out of scope
- Dynamic content from the API (AI-generated resume analysis, extracted resume text, raw error messages).
- URL-based locale routing.
- Backend/profile-level language persistence.

## Testing
- Manual: toggle language via the switcher on Landing and Settings, spot-check each migrated page in both languages for missing keys (untranslated keys render as the raw key with `react-i18next`, which makes gaps obvious) and layout breakage from longer pt-BR strings.
- `npm run lint` / `npm run build` after migration to catch unused imports and type errors.
